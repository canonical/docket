# AGENTS.md

## Commands

- `bun install`: installs the exact toolchain that `bun.lock` records.
- `bun run ci`: runs every gate below in order, and passes only when all of them pass. A pull request is ready when it passes locally.
- `bun run build`: type-checks the shipped sources with `tsconfig.build.json`, then compiles `src/application/main.ts` into one Linux x64 executable at `dist/docket`.
- `bun run check`: runs Biome's formatter and linter over the repository, then type-checks everything under `src/` and `guarantees/` with `tsconfig.json`.
- `bunx biome check --write`: applies Biome's formatting and safe lint fixes.
- `bun run test`: runs the unit tests with vitest under Bun.
- `bun run test:coverage`: runs them with v8 coverage, and fails below 100% of the lines, branches, functions and statements in `src/application/` and `src/lib/`, the application's stories aside: the `screens` guarantee draws them, not the unit suite.
- `bun run check:identity`: refuses home paths, personal logins outside the attribution fields, real repositories in fixtures, internal tool names, words that describe the project's history, and planning identifiers.
- `bun run check:secrets`: scans every commit and every staged or unstaged change with gitleaks. It uses `gitleaks` from PATH, or runs it through `nix run nixpkgs#gitleaks` when only nix is installed.
- `bun run check:audit`: refuses any dependency with a published advisory (`bun audit`).
- `bun run check:licences`: refuses any production dependency whose licence is not on the permissive list in `src/scripts/check-licences.ts`.
- `bun run check:structure`: checks the source tree's shape against the conventions below: exports and file names, barrels, folders, the direction of imports between domains, file length, and the guarantees corpus's reach into `src/`. In each `.ts` and `.tsx` file under `guarantees/`, it refuses an `import`, an `export … from` or an `import()` of a written relative path under `src/` to anything but a `*.stories.tsx` file, and an `import()` of a path it cannot read anywhere but in `guarantees/screens.test.tsx`, which loads the stories. It does not see `require()`, `import … = require()`, an absolute path, a `file://` URL or a file with another extension.
- `bun run self-test`: proves the identity, secret, advisory, licence and structure gates can each fail, by running each against a scratch fixture it must reject.
- `bun run guarantees`: runs the guarantees corpus's `pr` tier, `guarantees/corpus.toml`'s entries one at a time; `bun guarantees/invoker.ts run <entry> [test]` runs one, or only the test of it named.
- `bun run guarantees:accept <entry>`: runs one entry and saves what it prints under `guarantees/goldens/`; the only way a saved output is written.
- `bun run guarantees:prove`: breaks the corpus on purpose, one entry at a time, and requires each entry to fail for its break: a saved output moved aside for `text-output`, a request held open beside docket's for `request-budget`, recorded instants an hour late for `working-clock`, and for `screens` a saved screen moved aside, the colours left out of every screen, and each screen's fourth line moved up to second, which on owed's first frame draws the accordion above its selected row.
- `bun src/application/main.ts [command]` (or `dist/docket` once built): docket's text interface. `owed` (the default), `activity`, `show <reference>`, `assign <reference> <login>…`, `review <reference> <login or org/team>…` and `config`; `--help` after any of them gives its flags, an example and its exit codes. When a terminal gives both the input and the output, `docket` alone and `docket owed` without `--format` open the terminal interface on owed instead, grouped as `--by` names, and `docket activity` without `--format` opens it on activity, at the window `--window` names and the grouping `--by` names, as the same call would print; piped or captured, every call prints text. `↑` `↓` (`k` `j`) move the selection, which each mode keeps apart and which opens the thread's details under it; `⇞` `⇟` (Page Up, Page Down) move it by as many rows as the list shows, and `home` `end` to the first or last thread, none of them past either end; and `⏎` opens the selected thread's page, at the address GitHub gives, in the browser through `xdg-open`, saying on the status line when it cannot; in either mode, `a` opens an editor under the selected row to assign people to its issue or pull request, and `r` one to request reviews on its pull request: typing filters, `↑` `↓` move, `␣` ticks or unticks, `⏎` sets the whole set as `docket assign --confirm` and `docket review --confirm` do, and `esc` cancels. A key that cannot act on the selection, and a change GitHub refuses, say why with a `Recovery:` line. `?` lists every key and `q` quits.

## Conventions

- TypeScript is strict and resolves modules as `NodeNext`, so a relative import names its file with a `.js` extension.
- `tsconfig.json` extends `@canonical/typescript-config-react` and `biome.json` extends `@canonical/biome-config`. Change a rule locally only with a reason beside it.
- `src/application/` is the composition root and holds the executable's entry. `src/scripts/` holds the repository's gates, each with a `--self-test` mode, and `readEnvironmentWithoutGit.ts`, the one filter of git's variables that the self-tests and `src/testing/repository.ts` share. A self-test runs git, and any tool that runs git, without the caller's `GIT_*` variables, which would otherwise point it at the enclosing repository; `<gate>.test.ts` beside a gate that runs git proves it on a throwaway repository named through `GIT_DIR`.
- Each domain sits in its own folder under `src/lib/`, and a file is named for its role inside it: `lib/owed/rows.ts`, never `owedRows.ts`.
- An implementation file under `src/lib/` or `src/application/` exports one value, as its default, and is named after it: `rows.ts` holds `export default function rows`. It may also export the types of its own signature. `types.ts` exports only types and `constants.ts` only named constants.
- A folder's `index.ts` is a barrel: only named re-exports, such as `export { default as rows } from "./rows.js"`, reaching a file beside it or a child folder's `index.js`. It never uses `export *`, and no import uses a `#` path alias.
- No folder is named for a property, such as `utils/`, `helpers/`, `shared/` or `types/`. The exception is `common/` inside a terminal component under `src/lib/ui/`, which holds its subcomponents.
- Imports between domains point one way, and `src/scripts/check-structure.ts` holds the table: the model domains import only each other; the view models import the model, and activity also imports owed, whose field types and owner naming both lists share; the port imports the model's types; the adapter and the cache import the port and the model; the text, token and interface domains import the view models, the tokens and the port's types, and the text and interface domains also the cache's types, to show its status, and the model's types, to show a thread's facts and the settings in effect; the interface domain also imports the text domain's `sanitize`, so both faces make GitHub's text safe by one rule. Only `src/application/` imports everything. Nothing in `src/lib/` imports `src/application/`, `src/testing/` or `src/scripts/`, and nothing in `src/` imports `guarantees/`, nor anything in `guarantees/` `src/`, except its stories files (`*.stories.tsx`).
- Nothing under `src/lib/` reads the system clock. The current time is an argument, so every result is the same under test.
- The model domains derive everything from facts a provider records, such as who wrote a comment and when, and infer none. A rule GitHub does not apply, such as "the author is the assignee", is never applied here.
- The view models (`owed`, `activity`) give each piece of text as a field marked trimmed or wrapped, and never cut it to a width: only a face knows its width, and it measures display cells. They cap no field either: how much room a slot gets, such as the owner on a terminal row, belongs to the face that trims it, and a face that never trims shows every field whole. Each login they name, a row's author, every owner, the heading of an owner's section and the actor of an event, comes as a person: the login and one of five groups, `you` for the account gh is signed in with, else `team`, `internal`, `outside` (the settings' `external`) or `bot`, one group per login in each repository (`gatherPeople`): the settings' group, else `internal` once the organisation marks the login a member on anything it wrote there; a requested team is `you` when the personal file names it under `you.teams` (`you: { teams: [example-org/ui] }`, the teams the viewer belongs to, which only the personal file may declare) or a held thread shows the viewer among its members, and any other team and `unassigned` stay text. Text mode writes the groups in the settings' words.
- The GitHub provider takes its token only from `gh auth token`, and keeps it inside the provider: it reads no token variable and no file of gh's, and no result or error carries the token. Every request goes through Octokit's throttling and retry plugins, one at a time.
- The cache holds GitHub data only, never the token, in `$XDG_CACHE_HOME/docket` (or `~/.cache/docket`): a file readable by its owner alone, written whole as a temporary file renamed over the old one. One docket process fetches at a time, holding the `fetch.lock` there, and a process that takes the lock reads the cache again before it fetches. `patchAssignees` shows a thread's assignees before GitHub confirms them, in the process's memory only: never in the file, and any newer fetch or load replaces them. Its status carries each watched repository's stage in the last refresh the process ran (`RepoStage`: `waiting`, `checking`, `reading` with its pages, `checks` and `done` with the pages its read reached, `done` with its threads too, `paused` for the budget or for the rate limit, which also pauses every repository not yet fetched, or `failed` with the error that stopped it), reported by `fetchRepos` and kept once the refresh ends, and whether the refresh fetches everything whole while nothing is shown (`whole`).
- The cache reaches the data only through the provider interface, never the GitHub adapter. Its tests use `fakeProvider()` from `src/testing/provider.ts`, and prove what happens between processes by starting real ones, such as `src/testing/cacheReader.ts`, on a temporary folder.
- An error a user can meet carries a named code, one sentence and a recovery step. A code names the problem, as `GH_NOT_SIGNED_IN` and `CONFIG_INVALID_DURATION` do, and a domain lists its codes once, in its `types.ts`. Callers and scripts depend on the codes, so a code is never renamed or reused.
- The text interface exits 0 when it answered, cached data served during a GitHub or cache failure included, with the failure as a warning (`show` reads a thread's details from GitHub on every call, so it never answers from cached data alone); 2 for a `GH_*`, `CONFIG_*` or `USAGE_*` code; and 3 for any other code: no data, or a refused or partial write. `src/lib/text/chooseExitCode.ts` holds the rule.
- The help and the reading of the arguments are drawn from the command catalogue, `src/lib/text/catalogue.ts`, and nowhere else: a command, a flag, its choices or its default change there, with the hand-written help.
- Every string from GitHub or from a repository's file goes through `sanitize` before it is printed, and `llm` output marks it as quoted data: each title, login, team, label, check name, file path and branch in double quotes, and comments as `>` lines.
- `assign` and `review` print a plan and change nothing unless given `--confirm`, and never send a change that alters nothing.
- Both faces write a thread's set through `src/application/writeSet.ts` and nowhere else: it plans from the set GitHub holds, never the cache, sends nothing that alters nothing, refreshes the thread's repository in the cache after a change, reports `WRITE_INCOMPLETE` when GitHub records another set, and ends the recovery of a failure the provider says to refresh after with the face's own way to retry. The terminal's editors write through `src/application/writeFromTerminal.ts`, which shows an assignment on its row at once through the cache's `patchAssignees` and, once GitHub answers, the set GitHub records, taking the patch back when GitHub refuses; a review request shows once GitHub answers. An editor that cannot read whom to offer ends the provider's `step` with closing the editor with `esc`, refreshing with `R` and opening it again with its key, since `R` is off while it is open.
- Text mode reads threads, and activity's events, through the cache with `--max-age` (300 seconds by default) and never starts the refresh cycle.
- Each watched repository's `.github/docket.yaml` is read from its default branch through the cache with `--max-age`, as the threads are. An invalid one gives that repository the built-in defaults for the sections it may declare and marks its rows; one GitHub fails to give leaves the personal file's settings, with a warning. The terminal interface opens before it reads them, on the built-in defaults and the personal file, starts reading them after its first frame and applies them once they have all arrived, so a slow or unreachable GitHub never holds up the screen. It reads the login gh is signed in with apart from them, to mark the viewer among the people its lists name: when GitHub cannot say, the cached rows stay and mark nobody, the status line names the failure, and the read is tried again after the next sync. Text mode's `owed` and `show` read it too, after the threads, through the cache with `--max-age` as the files are, so a loop of calls asks GitHub for it at most once in that age, and write it as `you`; when GitHub cannot say and the cache holds no login young enough, they mark nobody and carry the failure as a warning.
- The terminal interface sits in `src/lib/ui/`, a folder per block under its kind (`layout/`, `subcomponent/`, `component/`, `pattern/`): `Name.tsx`, `Name.stories.tsx`, `Name.test.tsx`, `types.ts` and `index.ts`. A block takes its width as a prop and draws within it, trimming or wrapping with `trimText` and `wrapText`, which pass the text through `sanitize` and count display cells with `Bun.stringWidth`, never characters, so no text reaches the screen unfitted or with a control sequence in it. A login that comes with its group is drawn through `markPerson` in `src/lib/ui/`: the group's mark (`◉` you, `●` the team, `◐` the organisation, `○` outside, `■` a bot), a space, then the login, in the group's hue; the login gives way and the mark never does. A name without a group, such as `unassigned` or a team the viewer is not in, stays plain text, except in the review picker and in the status line that reports a request made from it, which name the organisation's other teams `◐` and a team `you.teams` names, or a held thread shows the viewer in, `◉`. The pane needs 40 columns and 8 lines (`minColumns` and `minLines` in `src/lib/ui/constants.ts`) and below either only says so, the width first.
- Stories follow Component Story Format, typed by `src/testing/stories.ts`, and the block's tests draw them through OpenTUI's test renderer with `draw()` from `src/testing/terminal.tsx`, asserting the characters and colours of each line at 40 columns and at one wider width.
- Every colour comes from `tokens` in `src/lib/tokens/`, which names meanings, never colours, and each colour on screen is paired with a symbol or a word. Bold marks a row's first line and nothing else, and italic a title.
- Keys are bound through OpenTUI's keymap, in two layers: the screen's global one, in `src/application/useScreenKeys.ts`, and the editor's, in `src/application/useEditor.ts`, which acts exactly while an editor is open and in sight, neither covered by the help nor hidden by a pane too narrow to draw it, whatever has the focus. While the pane is narrower than 40 columns or shorter than 8 lines and shows only what it needs, only `q` acts, and once it is large enough every key acts as before, on the selection where it was. While gh is missing or signed out, the screen is `setup`, titled so on its header in place of either mode, with the reason and its recovery in the list's place: no key changes mode or acts on a list there, and its key bar reads `? q quit`. While the help shows over the list, only `?` and `esc`, which close it, the movement keys, which scroll it (`useHelp` in `src/application/`), and `q` act, so no key acts on what the help hides. The help draws through the same `ScrolledList` as the lists, its group headings as headings and its key lines as rows, so a pane too short for it pins the heading of the keys at its top and counts the key lines below. While an editor is open, every global key but the help's is off, so typing reaches the filter, and while the help covers it, `?` and `esc` close the help, the movement keys scroll it, and no other key acts. Each command carries its help label (`desc`), its `group`, an optional key-bar `hint` and `notes`, and a command no key runs, such as typing into a filter, names what runs it in `shown`; the help and the key bar read them back with `useCommands`, so a key changes only where it is bound.
- The terminal interface starts the refresh cycle when it opens and stops it when it closes, in `src/application/openTerminal.tsx`, and nowhere else. It reads the cache's status and threads with `useSyncExternalStore`. The cycle follows the pane's attention (`createAttention` in `src/lib/cache/`): every key the screen hears counts, through a listener it puts ahead of the keymap's, and after `idleAfter` without one the pane is idle and the cycle runs every `idleInterval`, without the checks refresh or the whole hourly fetch; the next key still acts, and wakes the pane with a refresh at once. An idle pane still reloads what another process writes to the cache. Every interval is a named constant in `src/lib/cache/constants.ts`. Before the first data, the list shows `refresh in progress…`, a line for each watched repository with its stage (`RefreshStages`: `checking for changes`, `reading page 2/3` (`reading` alone until its first page says how many there are), `reading checks`, `✓ 89 threads`, `waiting`, `paused: budget low`, `paused: rate limit`, or `✗ failed: …` wrapped under the stage), the recovery of the failure a repository stopped on, and the progress line, counting the pages across the repositories begun once a first page says how many there are (`drawFirstRun`); why the fetch waits stands in while no repository has a stage, and when a failure no stage names shows the stages to be an earlier run's (`isEarlierRun`). While a refresh runs with the rows on screen, the status line names the furthest repository it has reached while one is under way, read from the cache's stages, and its place among those watched: `refreshing · docs 2/3`.
- owed's list is drawn by `src/application/OwedList.tsx` from the view model's groups, under owed's notice from `describeNoTeam` while the `people` in effect for a watched repository list nobody as team, which stays put as the rows scroll: whole blocks only, a heading or a row with its accordion, drawn through `ScrolledList` from `src/lib/ui/layout/`, which scrolls them with `useListScroll` and the pure `placeList` no further than the selected row needs, and back up as far as the room allows once it grows. While the first line shows a row of a group, the group's heading is pinned there with the place in the group of that row and the group's size, `● bob · 3 of 5`, on a line the list's height counts, unless the row is too tall to share the room with it. While rows are cut off below, the last line counts every one of them, in whichever group, dimmed: `↓ 4 below`, unless the first block is too tall to share the room with it. The selection is a place and the wait there (`placeSelection`), so it follows its wait as the clock, a refresh or a grouping reorders the rows, and never lands on a heading. The accordion reads a thread's details through the view's `readDetail` once for each copy of the cache's data, and a read that failed again when the selection comes back to its thread. It composes its lines from the snapshot, so `countAccordionLines` gives its height, at most `accordionMaxLines`, before any read; a line the details complete ends in a dimmed `…` and grows in place, and only a thread the snapshot holds nothing of says `loading…`, or, while reading is paused, when it resumes. Every read of details goes through `createDetailReader` in `src/application/`, at most `detailWindow` threads a request, and counts against `detailBudgetPerHour` (`src/application/constants.ts`): once the hour's budget is spent, only the selected thread's details are read, and the status line says `details paused`. While details asked for are unread, the status line's right side counts them, dimmed, as `details 3/12` (`describeDetails`), and hides the count on an error, on a refusal for the rate limit, while the refresh is paused, while the pane is idle and before the first data. `useReadAhead` reads the selected thread and the rows nearest it together, at once when the list first shows and `detailRest` after the selection rests, for those missing, out of date or `detailStaleAfter` old, and nothing while the pane is idle or the refresh paused; the accordion's own read joins the next request (`createDetailQueue`), which counts how many of the details asked for since nothing was pending have been read, and nothing while paused, and details read ahead reach it through `useHeldDetails` by moving the version it keys on. While the pane is active, `useSelectedWatch` checks the selected thread's repository every `selectedThreadInterval` with `refreshIfChanged`, and a thread it fetches that GitHub changed carries a new `updatedAt`, which reads its details again as any refresh does; an idle pane stops it.
- activity's list is drawn by `src/application/ActivityList.tsx` the same way, a thread's block holding its row, the accordion when selected, and its events. The accordion shows the thread's most pressing running wait as owed measures it, or, when none runs, the close body from the thread's details, the owners its row names or, for a closed thread, its assignees (`findThreadState`). Its selection is a place and the thread there, named by its reference, and each mode keeps its own in `src/application/Screen.tsx`.
- The terminal interface reads activity's events through the cache with the call's `--max-age`, in `src/application/useActivity.ts`, at each sync of the refresh cycle and for each window `t` steps to. It builds the list from the events it holds at every tick, so ages move with the clock without a read, and when a repository's read fails, the events the cache holds for it answer, however old and however far back, with the failure named in the status line; only when no repository has any does the failure stand in for the list.
- A source file stays within 500 lines, unless its first line reads `// Longer than 500 lines because …` with the reason.
- Every implementation file under `src/lib/` and `src/application/` has its own unit tests beside it, as `<name>.test.ts` (`.test.tsx` for a file holding JSX), with `describe` blocks named for its export; barrels, `types.ts` and `constants.ts` have none. Each `it()` states an outcome a caller can observe.
- Tests mock only at boundaries: the network, the filesystem, timers and `process`.
- A test waits for an outcome it can observe, such as a line on the screen or a call, with `waitUntil()` from `src/testing/wait.ts`, which leaves the time limit to the test, never with `vi.waitFor`, which gives up after one second. Unlike `vi.waitFor`, `waitUntil()` never moves faked timers between tries, so a test that fakes them moves them itself. A test that depends on the screen's clock fakes its interval and moves it on a tick, rather than sleeping through one.
- Tests of the GitHub provider stub `fetch` with `fakeGitHub()` from `src/testing/github.ts`, which answers with responses in the shapes GitHub gives, and run under fake timers, settling each call with `settle()` so the throttling plugin's waits pass at once. No test reaches the network.
- Tests of the text interface answer from `recordedProvider()` in `src/testing/recorded.ts` at `recordedNow`, and compare whole outputs line by line. `makeHome()` and `openSession()` in `src/testing/docket.ts` run a call, or one command, on a temporary configuration and cache.
- The guarantees corpus runs docket as its own process, `bun --preload guarantees/standIn.ts src/application/main.ts`, in a temporary home with a stand-in `gh` on `PATH`. The stand-in fixes `new Date()` at the instant a guarantee names and answers `fetch` from a recording under `guarantees/fixtures/`, written in GitHub's response shapes. With `GUARANTEES_UNTIL`, the stand-in lets each of docket's waits of a minute or more pass as soon as docket is quiet, so `open()` in `guarantees/makeHome.ts` runs a day of the terminal interface, in a pseudo-terminal, in seconds. A guarantee reads only the output, the exit code and the requests sent.
- A guarantee is a test file and a row in `guarantees/corpus.toml`. A missing saved output fails its entry, and the tier's `expect = "fail"` entry must fail for the tier to pass.
- The `screens` guarantee draws every story in `src/**/*.stories.tsx` through OpenTUI's test renderer at 40 and 60 columns, giving each block in the story the width, on the lines the story's `parameters.height` names or else 36, and at 32 columns the pane's `NothingOwed` and the screen's `Owed`, and compares each screen with its saved copy under `guarantees/goldens/screens/`: the characters of each line, then each run of text with its colours and attributes. A story added anywhere under `src/` is drawn from the next run, and fails until `bun run guarantees:accept screens` saves its copy.
- The composed screen's stories, `src/application/Screen.stories.tsx`, draw the real `Screen`, with the keymap, on the recording from `src/testing/recorded.ts`, from a cache held still (`holdCache()` in `src/testing/cache.ts`): one story for each state of the screen worth pinning, such as a grouping, the first run, the help or an open editor. A story's `run` names commands of the key layer to run once the screen opens, one at a time as their keys would, each once GitHub has answered the one before. An editor's story connects, for each drawing anew, to a stand-in for GitHub held in memory (`standInGitHub()`), so its writes reach nothing outside the process and no other drawing.
- Fixtures and examples use neutral names only: `alice`, `bob`, `example.com`, `example-org/example-repo`.
- Commit subjects follow Conventional Commits, with the domain as the scope. Commits are normal commits: no amending and no force-pushing.
- A pull request fills `.github/PULL_REQUEST_TEMPLATE.md`.

## Boundaries

- `package.json`'s `version` is the only place the version is written. The build reads it into the executable.
- `dist/` is build output and is never committed.
- Security reports go through GitHub's private vulnerability reporting, as `SECURITY.md` says, never through a public issue.

## Gotchas

- The build targets Linux x64 only.
- `src/application/main.ts` runs when it is imported: it is the program's entry, not a library module.
- vitest runs under Bun (`bunx --bun vitest`), the runtime the executable is built on, never under Node.
- vitest compiles JSX with oxc, so JSX options belong under `oxc` in `vitest.config.ts`; it ignores esbuild's.
- vitest resolves packages under the `bun` condition, so a test loads OpenTUI's Bun build, as the executable does: with its Node build beside, a renderer does not recognise the components React makes for it.
- A test of the terminal interface presses keys inside `screen.redraw(() => …)`, which lets React's updates settle before the screen is read back.
- A block that suspends, such as the accordion waiting on a thread's details, is drawn in its tests with `drawSuspending()` from `src/testing/terminal.tsx`: OpenTUI's `testRender` mounts inside a synchronous `act`, and React never retries a Suspense boundary that suspended there, so it would say `loading…` for ever.
- OpenTUI's own declaration files fail to type-check, so `tsconfig.json` skips declaration files; every source file is still checked.
- `src/scripts/check-identity.ts` holds the refused words, so it is the one file the identity check skips.
- The audit and its self-test query the advisory database, and the first gitleaks run through nix downloads it, so `bun run ci` needs the network.
- The throttling plugin spaces GraphQL requests a second apart, and the guarantees send them for real to the stand-in, so the tier takes about a minute.
- GitHub Actions does not run for this repository, so the local `bun run ci` is the gate: paste its output into the pull request's QA section.
